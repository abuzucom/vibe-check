# The list

## Code Quality

- Detect contradictory or impossible logic. For example, code that checks conditions after they've already been violated, or assumes states that are impossible given the control flow. Trace execution paths carefully. Ensure precondition checks happen before using values, validate ranges before checking impossible conditions, and don't check for states that the code has already ruled out.
- Avoid unintended global variable caching. In Node.js and Python servers, global variables persist across requests, causing data leaks and race conditions. Avoid storing request-specific data in module-level variables. Use request-scoped variables or explicitly mark shared caches as intentional.
- Guard against slow regular expressions. Regular expressions with nested quantifiers or ambiguous patterns can cause catastrophic backtracking and performance issues. Avoid nested quantifiers like (x+)+ and ambiguous patterns. Use atomic groups, possessive quantifiers, or rewrite complex regex patterns as simpler alternatives.
- Check divisor before division operations. Division by zero causes runtime crashes and must be prevented with explicit checks. Check if the divisor is zero before use. Add error handling for division failures, especially when the divisor comes from computation.
- Remove unreachable dead code. Unreachable code is confusing, untestable, and should be removed. Remove code that can never be executed due to control flow. Check for code after return/throw/break statements or in unreachable conditional branches.
- Avoid obvious performance drains. For example, code where computational cost grows unnecessarily with scale, nested loops creating O(n²) complexity, repeated work in loops, or hidden expensive operations. Move constant work outside loops. Use StringBuilder instead of string concatenation in loops. Cache compiled regex patterns. Use hash-based lookups instead of nested loops. Batch database operations instead of N+1 queries.
- Classes should have single responsibility. Classes handling multiple concerns violate the Single Responsibility Principle. Split classes that handle database, HTTP, and UI concerns into separate, focused classes.
- Use safe methods when removing from collections. Modifying a collection while iterating over it often causes bugs. Use iterator.remove(), removeIf(), or collect items to remove first then remove them after iteration. Avoid direct collection modification during iteration.
- Avoid recursion without depth protection. Recursion without proper depth limiting risks stack overflow and creates DoS vulnerabilities from malicious input. Recursion with enforced depth limits and proper bounds checking is acceptable. Add depth limiting via counter parameters that are checked and enforced, or replace with iterative approaches using explicit loops or stack data structures. For graphs, combine depth limiting with visited set tracking.

## Security

- Assume the codebase was built with AI tools. Look for patterns where convenience beats security. Focus on vulnerabilities that are common in AI-assisted development.
- Detect potential injection vulnerabilities. Never construct queries, commands, or code using string concatenation or interpolation of untrusted input. Always use parameterization, safe APIs, or proper escaping mechanisms. Use parameterized queries with placeholders, array-based command execution (no shell interpretation), or properly escaped arguments using vetted libraries. Avoid dynamic queries/commands built with user input concatenation.
- Don't use outdated hashing algorithms unless contextually justified. Avoid using outdated hashing algorithms (MD5, SHA-1) in any security-sensitive context. These are cryptographically broken, easy to brute-force, and harm system maintainability. Use modern alternatives: SHA-256/SHA-3 for general hashing, and bcrypt/scrypt/Argon2 (with salt and work factor) for passwords

## Style and Maintainability

- Handle errors in catch blocks. Empty catch blocks silently swallow errors, making debugging difficult. Add proper error handling in catch blocks. Log the error, show user feedback, or rethrow if needed.
- Don't place assignments inside conditionals. Mixing assignment and condition logic makes code error-prone and harder to understand. Separate assignments from logical checks. Check if the assignment is necessary within the conditional. In most cases the assignment is a typo or oversight. If the assignment is needed, refactor the code to separate the assignment from the conditional check.
- Use descriptive variable names. Very short variable names make code unclear. Use descriptive names for variables (except standard loop counters i, j, k and math variables x, y).
- Make a function's purpose self-evident. Functions without clear naming, documentation, or context are difficult for other developers to understand and use. Use descriptive verb-noun function names, add docstrings explaining the function's purpose, or provide meaningful return type hints.
- Don't overuse undocumented anonymous functions. Large anonymous functions without documentation are difficult to understand and reuse. Extract complex anonymous functions into named functions with descriptive names, or add explanatory comments for their purpose.
- Prefer simpler equivalent code. Logic written in a needlessly verbose way is harder to read and maintain than a clearly simpler equivalent. Rewrite the snippet in the simpler, behavior-equivalent form. For example, return a boolean expression directly instead of `if cond return true else return false`, avoid using lists when they are guaranteed to contain one element, etc.
- Avoid breaking public API contracts. Changes to public API endpoints that would break existing client requests are breaking changes. Support both old and new parameter names during transition periods. Add new optional parameters with defaults. Keep existing response fields while adding new ones. Focus on backwards compatibility.
- Avoid deep nesting levels. Deep nesting makes code hard to read and understand. Keep nesting levels under 4. Extract complex logic into separate functions when indentation exceeds 4 levels.
- Keep functions concise. Long functions are difficult to understand, test, and maintain. Break down long functions into smaller helper functions. Aim for functions under 60 lines with fewer than 10 local variables.
- Don't use break in inner loops. Break statements in deeply nested loops make control flow hard to follow without clear documentation. Add explanatory comments when using break in nested loops, or refactor complex nested loops into separate functions with return statements.
- Favor composition over inheritance. Deep inheritance hierarchies create tight coupling and make code harder to understand and maintain. Use composition, dependency injection, or interfaces instead of inheritance. Only inherit from framework base classes or when creating pure behavioral extensions without new state.
- Keep lines at a readable length. Lines that are too long are difficult to read and navigate, especially on smaller screens. Break long lines to enhance clarity. Aim for a maximum of 80-120 characters per line, depending on the context and coding standards.
